# Implementation status

The development plan is **in progress**. The repository has a working local collection path and a usable desktop UI, while several target-machine and hosted checks remain open. | 2 — OTLP and SQLite | Complete | All three Protobuf signals are decoded into protocol-independent batches and persisted through a storage package. Schema v14 migrates v1–v13; v10 stores canonical token counts, v11 adds exact Trace/Span correlation, v12 adds covering indexes for receipt-time counts and trace/span lookups, v13 adds nullable executable-path and command-line columns to process records, and v14 adds metric start time, temporality, monotonicity, and numeric aggregation JSON for Histogram, ExponentialHistogram, and Summary points. Existing metrics retain their scalar value and receive an empty aggregation object. The migration was verified on a full database copy and on the active database; the live pre-v14 backup passed `quick_check`. By 19:11 local time, live Codex had emitted 291 histogram points with valid persisted aggregation JSON, including count, sum, bounds, and bucket counts. Normalized span roles/process IDs, TTFT, span receipt time, and bounded sanitized ingest diagnostics are persisted. Retention defaults to 30 days, and the receiver port defaults to 4318 but is configurable from Settings. The API rejects unavailable ports before persistence; a changed port triggers a receiver restart. A bounded single-worker write queue and eight-request admission limit reject overload. The synthetic performance run accepted 10, 100, and 1,000 events/s and seeded 100,000 history events; measured refresh and pagination targets passed on this machine. |
| 3 — Codex adapter and sessions | Partial | Runtime OTLP batches pass through `internal/codexadapter`, which maps observed IDs, model/token fields, TTFT, tool calls, span roles, and process identifiers to canonical metadata before storage. Events inherit session/turn metadata from an exact matching Trace/Span in either signal arrival order; conflicting identifiers remain untouched, and events without usable identifiers or a matching span remain unassigned. `application.SessionQueryService` owns session, timeline, unassigned-event, tool-summary, and tool-call projections; `ProcessService` owns process projections. Session queries validate activity-time and model filters before reading storage. The tool explorer lists calls with session, time, tool and outcome filters, cursor paging, duration/status, retry metadata when supplied, and association quality. In the latest live sample, the latest 100 tool calls had no retry index. The fixed E2E now verifies command/test types and retry_index persistence; broader real Codex task-type/retry samples remain open. |
| 4 — Windows process monitor | Complete | An opt-in Windows collector samples configured roots and descendants at a configurable 250–2000 ms interval, records PID/PPID/start time/CPU/working set, tracks exits and PID reuse, and exposes settings/data through the API and process page. Two additional independent UI settings control executable-path and command-line capture; both default off. Paths replace the current user profile with `%USERPROFILE%`; command lines also mask common credential flags/environment assignments and are truncated to 4,096 runes, while the UI warns other arguments may contain sensitive data. Hourly cleanup removes expired exited processes and their samples, including when collection is disabled. Session detail now includes associated process records in a process tree. Tool associations use exact span PID when available, otherwise a unique parent/time/category match with lower confidence; ambiguous cases stay unassigned. Domain, storage, API, retention, and Windows child-process tests pass. An authorized Windows Flutter integration run enabled `codex.exe` monitoring from the Process page at 500 ms, kept path and command-line capture off, captured real Codex descendants, and saved monitoring back to disabled.
