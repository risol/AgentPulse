# Architecture review

Reviewed: 2026-10-23

This review compares the current repository with Explicit Architecture V1's ten principles in its [Chinese source document](https://github.com/risol/ExplicitArchitecture/blob/master/README.zh-CN.md) and the module boundaries in `AgentPulse-Development-Plan.md` section 10.1. The source document was checked on 2026-10-23. The principles are used as review questions, not as a requirement to reproduce a particular directory tree.

**Assessment:** nine principles are mostly aligned and one—layered feedback and continuous verification—is partial. The code-level boundaries are guarded and local checks pass. The latest isolated Windows UI E2E sent 20 logs (telemetry-to-dashboard P95 405 ms), ran a successful command, an expected failed command, and a test program, and confirmed matching UI/API/database counts. It also confirmed command/test tool types, retry_index=1 on the failed call, 3 explicit process PID associations, four persisted Codex roots, path/command-line capture off, and monitoring disabled afterward. Seven full-window 1600×900 screenshots were visually reviewed. Hosted CI, a multi-day representative retention/growth review, and broader live Codex retry/task samples remain open. Strict OS-level offline isolation was explicitly waived by the user on 2026-10-23; it was not performed or counted as passed.

## Current structure

The visible runtime path is:

```text
Flutter composition -> core/backend BackendSession -> Go child process -> SQLite initialization
Codex -> OTLP HTTP handlers -> decoding and privacy filtering -> telemetry.Batch
  -> codexadapter source normalization -> SQLite storage adapter -> schema/transactions
Flutter features -> core/api LocalApiClient -> authenticated loopback API
                                             -> application process/session/retention use cases
                                             -> process/correlation domains -> SQLite adapter
                                             -> Codex config operations
OTLP commit -> bounded telemetry change bus -> authenticated SSE -> debounced Flutter refresh
```

The desktop composition creates `core/backend/BackendSession`, validates the child-process handshake before constructing `core/api/LocalApiClient`, and injects API operations into feature modules. The API service owns bearer headers, JSON/status handling, SSE connection setup, and file downloads; the process service owns executable discovery, readiness timeout, loopback validation, and stdin/timeout shutdown. `features/dashboard/DashboardController` owns dashboard queries, filters, paging cursors, and loading/error state; `DashboardOverview` owns overview presentation; `DashboardRefreshCoordinator` owns polling, SSE reconnect, event debounce, and page-aware refresh selection. `features/settings/SettingsController` owns Codex configuration, retention, data export/clear, log cleanup, and diagnostic-export state and API calls. OTLP persistence now goes through a small `telemetry.Batch` model, a bounded worker queue, the `codexadapter` source mapper, and a storage adapter. Session, timeline, unassigned-event, tool-summary, and per-call queries are coordinated by `application.SessionQueryService`; timeline, unassigned-event, session-list, and process-list view models now stay out of the HTTP transport. `ProcessService` also maps session-associated process records for the session detail tree. Codex settings calls go through an application port implemented by the `codexconfig` command adapter. After a successful telemetry commit, a bounded change bus sends notifications over authenticated SSE, and Flutter debounces refreshes while retaining a polling fallback. Sanitized receiver errors are persisted with an allowlisted code and surfaced with queue state in the overview. Backend logs have allowlisted attributes, bounded rotation, expiry, and a settings cleanup action. An opt-in process monitor has its own domain package and Windows collector. The process page exposes separate default-off controls for executable-path and command-line capture, with profile and common credential redaction. The `application` package coordinates process configuration, session analytics/querying, global telemetry retention, ingest diagnostics, trends, timeline presentation, and Codex configuration; `correlation` owns the exact Trace/Span merge rule plus exact and heuristic process/tool association rules. Process history and individual tool calls are cursor-paged with filters. Schema v14 persists source-aware sessions, turns, tool calls, event association metadata, span receipt times/roles/process IDs, normalized token counts and TTFT, bounded diagnostics, optional process path/command-line details, and full numeric OTLP Histogram, ExponentialHistogram, and Summary aggregations with their start times, temporality, and monotonicity. Exact Trace/Span matches associate events across Logs/Traces in either arrival order; v12 adds covering indexes for the frequent trace/span and receipt-time queries, v13 adds nullable process detail columns, and v14 preserves metric distribution fields. Conflicting identifiers remain protected, and unmatched events remain visible through the paged unassigned-event API and overview UI. Session detail calls application analytics and process services, labels incomplete activity/request data as partial, and shows associated process records beside the waterfall timeline. Overview trend queries use fixed buckets and preserve unavailable values as gaps. Global telemetry retention is configurable in the UI and cleaned in bounded batches by a background application service. Settings, dashboard, tool-explorer, session-explorer/detail, process, chart, and waterfall presentation live in feature modules. `desktop/lib/main.dart` coordinates lifecycle assembly, navigation, confirmation dialogs, and native file picking. A Windows CI workflow and pure analytics package exist; real request links and lifecycle end markers remain unavailable.

The local API admission and authentication policy is explicit in `appapi.Server.authorize`: reject non-loopback Origins, apply the request bucket, validate the bearer token in constant time, then enter the route handler. The token bucket is owned by the application API transport; OTLP has independent payload and queue limits. `scripts/check-architecture.ps1` now also protects the protocol decoder, canonical telemetry, Codex adapter, and storage from importing upstream application or transport layers, and prevents analytics from depending on the Codex-specific adapter. The checker still verifies that the Go application layer does not import transport, storage, or source adapters, and that Flutter core/features do not cross their declared boundaries.

## Recommended dependency direction

```text
cmd/agentpulse (composition)
  -> telemetry / session / analytics / process domain
  -> application services
      -> domain rules and storage interfaces
  -> HTTP transports (OTLP and local API)
      -> telemetry or application interfaces
  -> SQLite adapter implements storage interfaces
  -> Codex adapter maps OTLP-specific attributes to domain records
```

The main remaining architecture work is verification rather than another local abstraction: validate the complete runtime paths on Windows and keep the new dependency-boundary check aligned with actual capability ownership. Dashboard, settings, and backend/API stateful workflows now have explicit modules; the app shell retains lifecycle assembly and user-facing platform interactions.

## Risks to keep visible

- The receiver, process sampler, retention service, and query API share a WAL-mode SQLite database through an eight-connection pool. The bounded ingest worker serializes telemetry batches while concurrent readers use separate connections; SQLite still serializes writes and applies a five-second busy timeout. Process sampling is opt-in; process rows use their own retention period. Telemetry records are pruned hourly with a separate configurable retention period. Application logs use bounded local rotation; physical database compaction remains a separate disk-space concern.
- Observed identifiers define source-aware session keys; events without a session identifier remain unassigned. These records should stay labelled as observed until stronger correlation rules are implemented.
- The Codex TOML editor uses a pinned unstable editor package. Keep its dependency isolated and verify upgrades against comments, formatting, and unrelated settings preservation.
- A process monitor must remain opt-in and must not change Codex permissions, sandbox behavior, or process execution semantics, as specified by the development plan.
