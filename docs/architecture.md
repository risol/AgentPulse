# Architecture

## Current implementation

The desktop starts an independent Go process and receives its API address, build version, and random token from a one-line stdout handshake. Its data path is:

```text
Codex -> loopback OTLP/HTTP receiver -> protobuf decoder
       -> privacy-filtered telemetry batches -> Codex adapter -> SQLite storage adapter (WAL)
Flutter -> authenticated dynamic loopback API -> application use cases -> process/correlation domains and SQLite ports
```

In Flutter, `main.dart` is the composition root. `core/backend` and `core/api` own child-process and authenticated HTTP behavior; startup diagnostics map a port conflict to a recovery message; `features/dashboard` owns query state, presentation, and refresh coordination; `features/settings/SettingsController` owns configuration and retention API workflows. The shell keeps navigation, confirmation dialogs, and native file selection.

The OTLP package decodes requests, applies the attribute allowlist, and creates source-aware telemetry batches. `codexadapter` maps observed Codex IDs, model/token fields, TTFT, tool outcomes, span roles, and process identifiers into canonical metadata before storage; SQLite persists this metadata without interpreting source-specific attribute names during normal writes or analytics queries. Historical-schema backfills remain source-aware migration code. A bounded single-worker queue persists batches; an OTLP response is successful only after commit. Requests that exceed the queue/admission capacity receive a retryable 503. After a successful commit, the receiver publishes a small update through a bounded coalescing event bus. An authenticated `/api/v1/events` SSE endpoint forwards these notifications; Flutter debounces refreshes and reconnects the stream, with polling retained as a fallback. Sanitized receiver diagnostics persist only signal, allowlisted error code, and timestamp, retaining at most the newest 200 records; queue depth/capacity/rejections and recent diagnostics are available in the dashboard. The settings page exports a separate JSON diagnostics bundle containing only application/schema version, receiver signal state, queue counters, and those sanitized diagnostic codes; it excludes event contents, process details, and Codex configuration. Backend JSON logs stay local, allow only reviewed metadata fields, rotate at 5 MiB across at most three archives, and expire after 14 days; the UI can clean expired archives. The Windows process package samples only configured root processes and their visible descendants when the user enables monitoring. Image names are always recorded for sampled processes; executable paths and command lines have separate, default-off switches in the process page. Paths replace the current user profile with `%USERPROFILE%`. Command lines also mask common credential flags and environment assignments, replace that profile path, and truncate stored values to 4,096 runes; other arguments may still contain sensitive content. Users can classify exact executable names and set 1–365 day process-history retention. The monitor prunes expired exited processes and their samples hourly, even while collection is disabled. The `application` package coordinates process settings, session analytics/querying, global telemetry retention, ingest diagnostics, analytics trends, and timeline view models; the `correlation` package owns the exact Trace/Span identifier merge rule and process/tool matching confidence rules. Process associations use explicit span PIDs when present, then a unique parent/time/category heuristic, and otherwise remain unassigned. The `storage` package owns SQLite schema initialization, transaction writes, exact cross-signal Trace/Span event correlation, and query methods. It remains one adapter package, with migrations, maintenance, session/tool/trend queries, telemetry persistence, and process persistence in separate `sqlite_*.go` files. The HTTP transport delegates session/timeline/trend query composition and view mapping to application services while retaining parameter decoding, status mapping, and response serialization. The API uses a separate ephemeral loopback port, a cryptographically random bearer token, and a strict route allowlist. The token is never logged or passed in command-line arguments. Codex TOML, process monitor, telemetry retention, database export, history clearing, and expired-log cleanup routes, plus session summaries/analysis, cursor-paged event/process records, tool summaries, and individual tool calls are available only through this authenticated API. Tool-call details include only allowlisted outcome/retry metadata and never tool payloads. Schema v14 persists source-aware sessions, turns, tool calls, spans, receipt times/roles, normalized input/output/reasoning token counts, TTFT, process identifiers, bounded diagnostics, optional process executable paths and command lines, and OTLP metric start times, temporality, monotonicity, and full numeric Histogram, ExponentialHistogram, and Summary aggregation fields. Exact Trace/Span IDs associate matching events across Logs and Traces in either arrival order, while conflicting IDs remain intact and unmatched events remain explicitly unassigned. Global telemetry retention defaults to 30 days, is configurable from 1–365 days, and runs as a bounded background cleanup independent from process-history retention. A database export is generated with SQLite `VACUUM INTO` as a consistent standalone snapshot; the UI asks the user where to save it. Clear-history deletes telemetry and process rows transactionally and preserves application settings. Session analysis currently uses an observed activity window and labels results partial when a true session end or request-level linkage is unavailable. Token/TTFT/output-rate/tool-duration trends use fixed-size storage buckets and preserve null samples. The receiver records a bounded inventory of observed OTLP attribute key names per signal in `app_state`; it never records values through this diagnostic path.

## Local service

The receiver defaults to `127.0.0.1:4318`; the Settings page can persist another loopback port in `app_state`. Before saving a changed port, the authenticated API checks that the port can be bound, then the UI restarts its backend child and refreshes the Codex endpoint preview from the actual listener address. Startup refuses non-loopback addresses. `/health` checks database connectivity and returns the schema version. The HTTP server uses bounded timeouts and requests are limited to 4 MiB. The desktop app starts the receiver directly as a child process and stops it when the UI exits.

The application API rejects non-loopback `Origin` values and compares bearer tokens in constant time. A token bucket limits API traffic to a 120-request/second refill with a 240-request burst; excess requests receive HTTP 429 and `Retry-After: 1`. The OTLP receiver separately limits concurrent exports, queue capacity, and payload size.

## Persistence

SQLite runs in WAL mode. Versioned schema initialization currently supports schema version 14, which contains telemetry, application state, process instances/samples, source-aware sessions, turns, tool calls, normalized token/TTFT fields, span receipt times/roles/process IDs, bounded sanitized ingest diagnostics, optional process paths/command lines, and OTLP metric aggregation JSON. Migrations advance v1 through v14; v4 adds canonical entity tables and observed association metadata, v5 adds a time-range index for tool analysis, v6 adds span receipt-time tracking for retention, v7 adds bounded ingest diagnostics, v8 adds canonical span role/model fields, v9 adds TTFT and process identifiers, v10 adds canonical input/output/reasoning token columns with a one-time allowlisted historical-data backfill, v11 adds exact cross-signal Trace/Span correlation, v12 adds covering indexes for signal/receipt-time counts and signal/Trace/Span lookups, v13 adds nullable process executable-path and command-line columns, and v14 adds metric start time, temporality, monotonicity, and Histogram, ExponentialHistogram, and Summary data. Older process rows keep NULL path/command-line values. OTLP batches and process snapshots are written in transactions. Process identity includes PID and start time, so PID reuse creates a new record. Missing timestamps and resource values remain SQL `NULL` rather than being represented as zero.

Schema v14 is the persisted model for the currently implemented telemetry, session, tool-call, process, and analytics features. Current Codex samples do not provide reliable session-end or project-path fields, and request-level linkage still needs broader validation; those source limitations are documented in `codex-integration.md`. Future schema changes must use explicit migrations.

## Dependency boundaries

`scripts/check-architecture.ps1` checks direct Go imports so application services do not depend on HTTP transport, storage implementations, or the composition root; domain packages stay independent from application, transport, and storage packages. It also checks Dart imports so `core` cannot depend on feature modules and feature modules cannot depend on `main.dart`. Windows CI runs this check alongside formatting, analysis, tests, and packaging. These rules protect the current dependency direction; they do not replace review of responsibility cohesion or runtime control flow.

## Privacy boundary

Raw OTLP request bodies, log bodies, span names, resource attribute values, prompt/output text, tool arguments, paths, and user identity values are not persisted. Span names are stored as the generic value `span`. Only the explicit attribute allowlist in the receiver is retained; string values are limited to 256 bytes, and only approved scalar values are stored. Metric names and units are limited to 128 bytes. The allowlist now includes observed model, tool, session/turn identifiers, token counts, TTFT, outcomes, and selected Codex metadata. The observed key inventory can include names like `user.email` or `arguments`, but stores no values. Review this allowlist whenever Codex telemetry changes.

Database export contains this same locally stored, allowlisted telemetry and process history. It is a complete database backup, not an anonymized diagnostics bundle. The clear-history action permanently deletes telemetry, session, tool-call, and process records while retaining application settings.
